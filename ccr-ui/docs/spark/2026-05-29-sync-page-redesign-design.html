Sync Page Redesign Design Spec

  • Date: 2026-05-29
  • Topic: CCR UI WebDAV sync redesign
  • Status: Written spec for user review

Summary

Redesign the sync page from a generic folder-selection tool into an editorial, high-density configuration asset console. The sync surface should focus on a fixed manifest of allowed CCR, Claude Code, and Codex configuration assets; remove Gemini and Antigravity from this page; and support both single-item synchronization and one-shot all-item synchronization.

Chosen direction: “Editorial Control Desk” with warm neutral surfaces, compact asset cards, clear risk copy, and direct per-item operations. This matches the ccr-ui design guidance for a calm, precise, Anthropic-like workbench rather than a dark/glassy operations terminal.

Goals

  • Synchronize all CCR platform configuration content under ~/.ccr/platforms/, especially Claude and Codex auth, base URL, provider routing, and key-related fields already represented by CCR platform configs.
  • Synchronize only the Claude Code user config files ~/.claude/settings.json and ~/.claude/CLAUDE.md; do not synchronize the full ~/.claude directory.
  • Synchronize only the Codex user config files ~/.codex/config.toml and ~/.codex/AGENTS.md; do not synchronize the full ~/.codex directory.
  • Use canonical Markdown names in the product model: CLAUDE.md and AGENTS.md. On Windows, locate case-insensitive variants such as claude.md, Agents.md, or agents.md and normalize the remote item display to the canonical names.
  • Allow each asset to be pushed, pulled, or synchronized independently, and allow a single “sync all once” operation that runs the fixed manifest in a predictable order.
  • Display sensitive config content only as masked summaries or field categories; never expose raw auth tokens, API keys, or bearer tokens in list rows, logs, or status summaries.

Non-goals

  • No Gemini or Antigravity sync entry in this page. Existing Gemini/Antigravity features elsewhere are outside this spec.
  • No generalized arbitrary folder backup redesign. Custom folders may remain a later feature, but the primary sync page for this cycle is fixed configuration assets.
  • No automatic background sync, file watching, scheduled sync, or cross-device merge editor in this cycle.
  • No full-directory restore of ~/.claude or ~/.codex, because these directories contain caches, sessions, credentials, tool state, agents, plugins, and other data outside the requested scope.
  • No new sync transport beyond the existing WebDAV direction unless implementation later proves WebDAV-client limitations block the acceptance criteria.

Context

Current ccr-ui sync is centered on src/views/SyncView.vue and a set of folder-oriented components such as SyncSelectionPanel.vue, SyncEnabledFoldersPanel.vue, SyncBatchOperationsPanel.vue, and SyncOperationOutputPanel.vue. The page currently treats CCR platforms as a required folder, offers Claude as a whole ~/.claude/ folder, and includes an Antigravity-branded Gemini item. The Tauri sync commands support all-folder push/pull and per-folder push/pull, while ccr-sync already has a directory push path that can filter uploads with allowed_paths, but the current Tauri folder push path calls it without an allowlist.

External references support the requested file boundaries. Anthropic documents ~/.claude/settings.json as the user-level Claude Code settings file and identifies CLAUDE.md files as memory/instruction files loaded by Claude Code. OpenAI documents ~/.codex/config.toml as the Codex user-level configuration file and ~/.codex/AGENTS.md as global persistent Codex guidance. WebDAV RFC 4918 states that PUT to an existing resource replaces the resource and recommends conditional mechanisms such as entity tags to avoid lost updates, which informs the spec’s explicit overwrite, backup, and conflict-status requirements.

Recommended Approach

Implement a manifest-based sync model and render it as a configuration asset console. Each asset has a stable id, product group, local path resolver, remote path, display metadata, sensitivity policy, and operation state. The UI reads this manifest, displays grouped asset cards, and calls Tauri commands that sync either one manifest item or the full manifest once.

Manifest item Local target Remote target Notes
ccr-platforms ~/.ccr/platforms/ platforms/ Directory item. Includes all CCR platform configs and must preserve Claude/Codex provider auth, URL, and key-related settings.
claude-settings ~/.claude/settings.json claude/settings.json File item. Mask sensitive env/auth values in summaries and operation output.
claude-memory ~/.claude/CLAUDE.md claude/CLAUDE.md File item. Case-insensitive local lookup on Windows; canonical display and remote name remain uppercase.
codex-config ~/.codex/config.toml codex/config.toml File item. Treat auth/provider fields as sensitive and avoid raw log output.
codex-agents ~/.codex/AGENTS.md codex/AGENTS.md File item. Case-insensitive local lookup on Windows; canonical display and remote name remain uppercase.

Alternatives

Option Why not chosen
Keep the folder model and add include/exclude filters This is less disruptive but keeps the mental model as “sync folders,” which conflicts with the safety requirement to avoid whole .claude and .codex directories. It also makes per-file status and copywriting weaker.
Archive each group into a bundle before upload Bundles make remote storage tidy, but they make single-file pull/push, status checks, conflict display, and local backup behavior more opaque.
Retain the current dark/glassy operations UI and only change item definitions It would satisfy part of the data-scope request but misses the requested page redesign and conflicts with the project’s calm editorial visual direction.

  • Header: title, short scope statement, WebDAV connection badge, “check status,” and “sync all once.”
  • Main column: grouped cards for CCR Platforms, Claude Code, and Codex. Each card lists only the manifest assets in scope.
  • Side column or lower responsive panel: WebDAV endpoint health, last run summary, conflict count, backup location hint, and compact operation output.
  • Visual style: warm neutrals, charcoal text, subtle borders, editorial spacing, minimal accent colors for status only, no purple-led gradients, no heavy glassmorphism.

Frontend responsibilities

  • Replace the platform-selection panel with a manifest-driven SyncAssetConsole or equivalent page-level composition.
  • Render asset groups and actions from typed data rather than hardcoded “optional platform” cards.
  • Show item state: local exists, remote exists, last operation, modified hint if available, disabled/missing state, and conflict/force warning.
  • Keep operation output terse and masked. Logs should name item ids and file names, not raw config values.
  • Remove Gemini/Antigravity strings and routes from the sync page copy and selection state.

Tauri and sync responsibilities

  • Add manifest-aware commands such as sync_list_assets, sync_push_asset(id, force), sync_pull_asset(id, force), sync_sync_asset(id, force), and sync_sync_all_once(force). Exact names can follow existing API naming conventions during implementation.
  • Expose a safe path resolver that expands ~, validates fixed allowed roots, handles Windows case-insensitive canonical Markdown lookup, and rejects ids outside the manifest.
  • Use single-file push/pull for Claude and Codex file assets. Use directory push/pull for ccr-platforms, preferably with explicit directory identity rather than a generic user-added folder.
  • Before pull overwrite, create a timestamped backup of the local file or directory. For file assets, back up the existing file next to the target using the same style as current directory backups.
  • Use remote-exists checks and force semantics consistently. When practical with the WebDAV client, capture ETag/modified metadata for conflict warnings before replacing remote content.

Control flow

  1. Page load requests manifest asset status from Tauri.
  2. Tauri resolves local canonical paths, checks local existence, checks remote existence, and returns masked metadata.
  3. User triggers Push, Pull, Sync, or Sync All Once.
  4. Frontend disables only the affected item or all items for global operation, streams or appends concise progress, and updates status after completion.
  5. On conflict or overwrite risk, UI shows an explicit force action and describes the backup path before retrying.

Risks

  • Secret leakage in UI or logs: mitigate with masking utilities, no raw JSON/TOML dumps in operation output, and tests that reject common secret-like patterns in rendered summaries.
  • Unexpected overwrite through WebDAV PUT: mitigate with remote-exists checks, explicit force copy, local backups before pull, and ETag/modified metadata when available from the WebDAV client.
  • Case-sensitive filename mismatch across systems: mitigate with canonical display names and platform-aware lookup that accepts case-insensitive variants on Windows while preserving canonical remote names.
  • Migration from existing folder config: existing users may have old claude or gemini sync folders. The page should ignore Gemini/Antigravity for the new manifest and avoid deleting old config silently; cleanup can be explicit in a later migration step.
  • CCR platforms directory contains sensitive provider data: this is in scope by user request, so the UI must clearly mark it as sensitive and avoid previews that reveal values.

Test/Acceptance Criteria

  1. The sync page displays only CCR Platforms, Claude Code, and Codex sync groups; Gemini and Antigravity do not appear on the page.
  2. Claude sync status and operations include only settings.json and CLAUDE.md; a fixture with extra files under ~/.claude proves they are not pushed or pulled.
  3. Codex sync status and operations include only config.toml and AGENTS.md; a fixture with extra files under ~/.codex proves they are not pushed or pulled.
  4. Windows case-insensitive lookup recognizes claude.md, Agents.md, and agents.md while presenting canonical remote names.
  5. Each manifest item can run independently and update only its own loading/result state.
  6. “Sync all once” runs the complete manifest in a stable order and reports per-item success/failure without stopping the UI from showing partial results.
  7. Pull overwrite creates a local backup before replacing an existing local target, and the backup path is visible in the operation result.
  8. Operation summaries and visual cards mask auth, token, API key, bearer, and base-url-with-key patterns.
  9. Frontend verification for the implementation phase should include focused component tests, i18n checks for added strings, bun run type-check, and bun run test; if backend commands change, add targeted Rust tests and run the relevant Tauri check command.
  10. Visual acceptance: the page follows the warm editorial direction, supports light and dark themes, remains readable at narrow widths, and avoids the previous heavy glass/purple styling.
