Evidence Dossier + Decision Matrix

VibeDeck vs ccr-ui：从 usage 后端与 app 前端看优化方向

核心结论：VibeDeck 的真正优势不是“图表更多”，而是它把 usage 这件事做成了一个统一、实时、可追责的域模型： active session → provider → repo / worktree / branch → canonical ledger → live operations。 ccr-ui 已经拥有更广的多工具 control plane，但 usage 子系统目前仍偏“报表聚合 + 双链路拼装 + 弱实时”。 最值得借鉴的不是照搬页面，而是把 usage 变成可操作的工作台。

范围：VibeDeck 本地代码快照 vs ccr-ui 当前实现 方法：代码证据优先，推断单独标记 结论可信度：高 注意：VibeDeck 并不基于 llmusage，上下文是“本地 usage intelligence 模式对比”

执行摘要

VibeDeck 最强优势

统一 usage 主线

后端有 canonical ledger，前端有 live / branches / usage 连续叙事，诊断、stale、override 都围绕同一条主线展开。

ccr-ui 当前长板

更强的多工具控制面

不只看 usage，还覆盖 CLI 管理、配置、监控、配额、session、插件与平台操作；能力面比 VibeDeck 更宽。

后端最高 ROI

加一层 usage snapshot / source health 投影

把现有按请求重算的 overview / trends / model / project / diagnostics 汇总成可缓存投影，并用导入事件失效。

前端最高 ROI

把 usage 页改成 ops cockpit

先回答“是否可用、数据新不新、哪一路坏了、下一步做什么”，再展开趋势、模型、项目和日志明细。

关键判断： ccr-ui 不应该把自己变成另一个 VibeDeck。正确方向是：保留“多工具 control plane”的产品定位， 但把 usage 子系统升级到更像 VibeDeck 那样强主线、强实时、强健康度、强 drilldown。

VibeDeck 的主要特色

特色 1

Local-first + canonical ledger

README 与 PROJECT 明确把 SQLite canonical store 当成产品中心，而不是临时缓存。多 provider 数据被吸收到一套稳定读模型里。

证据：ref/repo/VibeDeck/README.md、PROJECT.md、src/lib/usage-read-models.js

特色 2

Live workbench，不是静态报表

首页默认就是 live workbench，前端通过 SSE + last-good cache 持续显示 live sessions、workstreams、stale / reconnecting 状态。

证据：dashboard/src/pages/LivePage.jsx、dashboard/src/hooks/use-vibedeck-live-sessions.ts、src/lib/local-api.js

特色 3

Branch / repo / worktree 归因深度更强

VibeDeck 把 usage 归因一路钻到 repo、branch、session，还提供 branch override，明显不是“按平台 / 模型看统计”就结束。

证据：dashboard/src/pages/BranchesPage.jsx、dashboard/src/pages/LivePage.jsx、src/lib/sessions/*

特色 4

Honest unknowns + diagnostics first

它明确保留 unknown / historical unknown，不伪造精度；同时把 sync freshness、canonical completeness、source 状态当作一等信息。

证据：PROJECT.md 的 release audit，src/lib/local-api.js，dashboard/src/lib/sync-freshness*

特色 5

所有 surface 讲同一个故事

web dashboard、CLI、Mac app、widgets 都围绕同一条 usage narrative 展开，不会出现“首页说一个世界，明细页说另一个世界”。

证据：README.md、dashboard/src/App.jsx 路由、src/commands/serve.js

后端：ccr-ui 的 llmusage / usage 实现分析

先说优点： ccr-ui 的 usage 后端边界其实很健康。 src-tauri/src/llmusage_adapter/mod.rs 明确坚持 crate-free、只读 SQLite、只调已安装 CLI； capabilities.rs 有 typed unsupported reason； commands/usage.rs 也已经把 overview / trends / model / project / source / heatmap 聚合成单个 dashboard API。 这说明基础边界比“随手绑一个三方库”成熟得多。

已验证的强项

  • 强约束：不链接 llmusage crate，不写 llmusage DB。
  • feature capability 明确，unsupported 状态可解释。
  • 导入任务有 recent_ready / finished 阶段。
  • home overview 已能把 usage 与 session 数串起来。

主要结构性缺口

  • 首页依赖 llmusage usage + ccr session archive 双链路拼装。
  • dashboard 每次查询仍现算多个投影。
  • 缺少 live usage summary channel。
  • project 之下没有 repo / branch / session drilldown。

与 VibeDeck 的本质差距

不是 SQL 少几张表，而是缺少一个“usage 运行态事实层”。 VibeDeck 先建 canonical model，再做页面；ccr-ui 目前更像先有页面需求，再从两个本地数据源现拼 payload。

VibeDeck 的优势是 usage 域模型统一、实时、可追责；ccr-ui 的优势是多工具 control plane 更强。最高 ROI 的优化是：后端加 usage snapshot 与 source health 投影，前端把 usage 页改成先讲可用性与健康度的 ops cockpit。
后端 P1 影响：高 成本：低到中

1. 在 Tauri 后端补一层 usage snapshot cache

把 get_usage_dashboard_v2 的 summary / trends / model / project / source / archive / heatmap 聚合结果按 platform + start + end + include_heatmap 做短 TTL 缓存，并在导入事件后失效。

为什么这是最高 ROI

现在前端 stores/usage.ts 有 30 秒缓存，但后端没有同级 snapshot。 这意味着同一窗口内重新进页、跨组件取数、后台 warmup 后主动刷新，都会再次触发阻塞查询。 这是最容易补的一层“像产品而不是像 demo”的稳定器。

后端 P1 影响：高 成本：中

2. 把 source health 变成一等投影，而不是附带诊断

你已经在 llmusage_adapter/db.rs 里有 diagnostics() 与 per-source live / missing / deleted / recent_completed_at / history_completed_at；下一步应该把它折进 dashboard payload 顶部结构，而不是只作为 warning 或日志背景信息。

建议的最小 contract

建议返回：source、最近成功同步时间、history 完成时间、live 文件数、missing 文件数、deleted 文件数、当前导入阶段、是否 capability unsupported。 前端就能直接画 source health strip，不必再从多个 warning 文本推导。

后端 P1 影响：中到高 成本：中

3. 降低首页双链路拼装的临时性

get_home_usage_overview_v2 当前在请求时动态合并 llmusage usage 与 ccr_db session archive。 这在过渡期是合理的，但长期会让首页的“真相源”越来越难解释。

建议做法

不是立刻重写 schema，而是在本地先做一个 home_usage_snapshot 级别的缓存投影： usage truth 仍来自 llmusage，session truth 仍来自 ccr_db，但输出成为一份有时间戳、可失效、可解释的稳定快照。

后端 P2 影响：高 成本：中到高

4. 用 Tauri 事件补“live usage summary”而不是只靠导入后刷新

ccr-ui 已经有 usage job progress 事件，但还没有一个“当前 usage 总览正在变动”的稳定前端消费模型。 可以不学 VibeDeck 的 SSE，而是利用 Tauri emit 推送增量 summary / freshness / source-state 变化。

后端 P2 影响：高 成本：高

5. 规划 repo / branch / session 级 drilldown，而不止 project

VibeDeck 最有辨识度的不是 provider 数量，而是把 usage 和真实工程结构绑定。ccr-ui 已经有 session index 与 project_path， 下一阶段可先做到 project → session，再追求 repo / branch。

后端 P3 影响：中 成本：低

6. 修复“unknown 默认归到 Claude”的诚实性瑕疵

src-tauri/src/stats_snapshot.rs 的 normalize_usage_platform() 对未知值默认回落到 claude。 这与 VibeDeck 在 unknown bucket 上的诚实策略相反，建议改成独立 unknown 桶。

前端：ccr-ui app 的 usage 体验与工作台设计

我对前端的判断： ccr-ui 的 usage 页面已经不弱，甚至在“多 tab 分析能力”上比很多工具更完整； 但它目前更像一个分析 dashboard，还不是一个usage operations cockpit。 VibeDeck 的启发是：把“数据是否可信、系统现在处于什么状态、下一步做什么”放到第一屏。

ccr-ui 已有的前端优点

  • DashboardView.vue 已是 task-oriented，而非纯装饰首页。
  • UsageDashboardView.vue 覆盖 overview / tokens / cost / models / projects / logs。
  • useUsageDashboardState.ts 做了 locale gating、idle hydration、chart lazy load。
  • MonitoringView.vue 已有可用的健康日志工作台。

相比 VibeDeck 的主要缺口

  • usage 第一屏缺乏“新鲜度 / 健康度 / 当前任务”强反馈。
  • source 诊断存在，但不够前置。
  • 页面是 tab-first，而不是 state-first。
  • usage、monitoring、quota/budget 之间联系不够紧。

一句话方向

把 usage 页从“统计图入口”升级成“当前 AI CLI usage 运行台”： 先讲 readiness、freshness、source health、active import，再展开趋势、模型、项目和日志。

前端 P1 影响：高 成本：中

1. 重写 usage 页首屏：先状态，再分析

建议把当前 toolbar + meta + warning 堆叠，改成一个 Usage Ops Header： freshness、当前导入阶段、source health、archive 状态、下一步 CTA。

推荐首屏信息顺序
  1. 数据新鲜吗？最后一次 recent / history 完成时间是什么。
  2. 现在是否正在导入或回填？
  3. 哪一路 source 正常、缺失或脏。
  4. 如果坏了，用户该点哪里：导入、修复、看日志、去平台页。
前端 P1 影响：高 成本：中

2. 把“warning 文本块”替换成结构化状态卡

当前页面中 importJobBanner、unsupportedSyncMessage、warningMessage 都是文本驱动。 更建议做成结构化卡片：状态、来源、最近时间、影响范围、CTA。

前端 P1 影响：中到高 成本：低到中

3. 把 stale / cached / background refresh 做成明确体验

你已经在 store 里做了 dashboard cache，但用户未必知道自己看到的是新结果还是旧缓存。 可以借鉴 VibeDeck 的 reconnecting / stale banner，把“这是上次可用数据”说清楚。

前端 P2 影响：高 成本：中

4. 从 tab-first 改成 split-view：概览 + 操作

现在 overview / tokens / cost / models / projects / logs 的 tab 切换很完整，但第一屏过于“分析工具感”。 更好的结构是左侧主图表与 summary，右侧固定 operations / diagnostics / source health。

前端 P2 影响：中到高 成本：中

5. 把 monitoring 与 usage 关联起来，而不是平行存在

MonitoringView.vue 很强，但 usage 页只在 logs tab 末端触达问题。 建议在 usage 页直接显示最近 usage import 失败、最近 source 缺失、最近 repair 建议，并深链到 monitoring。

前端 P2 影响：中 成本：中

6. 用 usage 统一 budget / quota / platform health 的语言

ccr-ui 里预算、Codex quota、平台 readiness、usage 分析目前分布在不同页面。 用户会把它们理解为同一件事：这台机器上的 AI 工具现在还能不能继续跑，成本是否健康。

前端 P3 影响：中 成本：中

7. 做 project → session → raw log 的渐进钻取

在后端尚未完全 branch-aware 前，前端也可以先支持 project 卡片进入 session 列表，再进入日志明细。 这会比继续堆 tab 更接近真实工作流。

前端 P3 影响：中 成本：低到中

8. 视觉层面再收敛：更少“提示块”，更强“编辑部式层级”

ccr-ui 的整体设计方向已经是 calm / precise / editorial。 usage 页可以进一步减少重复容器和杂讯，把状态胶囊、关键数字、下一步操作做得更像同一套工作台语言。

建议路线图

Phase 1 · 1–2 次迭代 以低风险高收益为主

先把“状态是否可信”做扎实

  • 后端增加 usage dashboard snapshot cache。
  • dashboard payload 加入 source health / freshness。
  • usage 页首屏改为 readiness + freshness + import state + CTA。
  • 显式 stale / cached banner。
Phase 2 · 2–4 次迭代 把 usage 做成可操作工作台

建立 usage ops cockpit

  • usage 页 split-view：左分析，右操作 / 健康度。
  • monitoring 深链与最近失败项前置。
  • home overview 与 usage 页共用同一套状态语言。
  • 补 Tauri 事件驱动的 live summary / freshness 更新。
Phase 3 · 中期能力建设 需要后端维度扩展

把 usage 从“按平台统计”推进到“按工程结构归因”

  • 先做 project → session drilldown。
  • 再规划 repo / branch / worktree 级归因。
  • 逐步减少首页的双链路拼装感。
优先级建议： 如果你只能先做一件事，我建议先做后端 source health + snapshot cache，再做usage 页首屏重构。 原因很简单：没有稳定且可解释的状态层，前端再好看也只是把不确定性包装得更漂亮。

证据 vs 推断

已验证事实

  • VibeDeck 使用 canonical SQLite usage ledger 与 live SSE。
  • ccr-ui 的 llmusage 边界是 crate-free + read-only。
  • ccr-ui 首页 overview 由 llmusage usage 与 ccr session archive 现场合并。
  • ccr-ui usage 页已有完整 tab、缓存、日志分页与后台导入任务。

推断与建议

  • 用户会把 source health / freshness 理解为 usage 页的头号信息，而不是附属 diagnostics。

  • branch / session drilldown 是 ccr-ui usage 差异化的下一个关键增量，但不应早于 snapshot / health 基础层。
