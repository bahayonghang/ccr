# S2 real runtime source — minimal boundary proposal (not implemented)

Historical proposal status: subsequently implemented in the S2 batch. Current
source, checks and remaining native/performance limits are recorded in
`performance-s2-implementation-20261106.md` and
`performance-s2-check-20261106.md`. The proposal text below records the boundary
before implementation; it is not the latest execution receipt.

The common clock/admission implementation batch is complete and separately receipted. This document proposes the next smallest source changes; it does not claim a stream, real 1000/s delivery, GUI operation or performance sample has run.

## Existing paths actually inspected

- Native `runtime/monitoring.rs::Owner::record` sanitizes a real MonitoringEntry, retains it in a ring bounded to 500 entries/512 KiB, counts ring evictions, then calls captured `LogPersistenceService::append_entry_with_connection`. Today it is private, returns unit and exposes only the last write outcome. Lifecycle `terminal` constructs entries and invokes this path; `Requests::refresh` merges persisted and retained entries for the actual feature.
- Tauri `monitoring.rs::record_monitoring_entry` calls `AppState.event_log.push(AppEvent::Monitoring)`, conditionally calls `state.monitoring_logs.append_entry`, then emits `app:monitoring`. Its EventLog is bounded to 500 entries/5 MiB, rejects >10 KiB events, and counts oversized drops, but does not acknowledge individual insertion/eviction. `LogPersistenceService` buffers at threshold 20, flushes through the already captured global main pool, logs storage errors and returns unit. `record_monitoring_entry` also returns unit. Consequently counting a call as actual ring/persistence delivery would be false.
- Both persistence routes already end in the existing ccr-db log_repo owner. No new log SQL or second event store is needed. The actual native ring/UI cap differs from Tauri; the workload must report those evictions rather than silently equalizing real app policy.

## Proposed smallest implementation

1. Add a fixed S2-only source under `ccr-app::benchmark::s2`, using the existing runtime/Tokio/cancellation facilities and pinned dependencies. No generic plugin/sink framework. A source has deterministic event IDs/content/logical timestamps from the captured manifest clock plus slot index, and a fixed versioned 1000 slots/s, 60-second schedule. Actual schedule/rate/elapsed/late measurements use real monotonic Instant. No rows or 60000-entry array are prefilled.
2. Source production is one retained run with a bounded small queue (e.g. 128), not a job per event. A 1ms schedule uses deadlines and skip-on-overrun behavior: slow scheduling/sinks never cause a catch-up burst that is called 1000/s. Each actually attempted slot, missed schedule slot, queue acceptance/rejection and sink outcome is counted. Report requested rate separately from actual attempted/delivered rate, queue drops, skipped/late slots, ring evictions, persistence errors, run elapsed and terminal reason. Intended event slots/payloads are identical across endpoints; accepted subsets may differ and must be visible.
3. Add compatible acknowledgements to the two existing monitoring paths, retaining existing unit wrappers for ordinary callers. Native returns actual retention/write outcomes from its current record body. Tauri EventLog returns accepted/oversize/evicted information; a checked persistence flush path reports attempted/committed/failed counts, including final drain; emit failures are counted separately. Reuse original owner behavior/transactions and explicit captured pool. Do not equate queue acceptance, ring retention, emission, or durable persistence. An explicit workload persistence policy must be agreed and recorded; the simplest comparable S2 contract is persist=true in both endpoints, while preserving each endpoint's real existing batching behavior.
4. Trigger only by a dedicated explicit Benchmark/S2 runtime action: start/status/cancel on the existing retained owner. Local and old Fixture, S0/S1, unvalidated or already-running sources reject before allocation/effects. Tauri can expose narrowly registered benchmark-only IPC actions; native uses the matching existing app action/runtime seam. Startup validation/imports never start the producer. A future harness invokes start after the desired app state is ready; starting a source is not a first-present measurement. No GUI is to be launched for implementation tests.
5. The application owns producer+consumer handles after view detachment. Cancellation/quit stops production, drains or explicitly counts remaining queued events according to the declared contract, flushes acknowledged persistence, and joins both sides through existing runtime shutdown. A terminal snapshot cannot say success until joined cleanup completes. New trials restore original static inputs after owners stop; nonempty WAL and changed main DB are not silently accepted as original seed.

## Narrow verification before any native sample

Synthetic tests cover closed source admission/no auto-start, deterministic event payloads/IDs, bounded queue/drop accounting, real monotonic paced short runs without rate-threshold claims, slow sink overruns without catch-up fiction, late cancel/view detach/quit join, final flush failures and untouched alternate roots. Both adapters must consume real MonitoringEntry values through their existing owners, read back ring/persistence counters and actual records, and keep ordinary behavior unchanged. A shortened test profile is a test fixture only; it must not mutate the production 60-second/1000-slot contract or count as its result.

No startup/first-present/input/memory/energy success follows from implementing this source. Native sampling remains user-deferred. GPUI CPU attempt/on-next-frame is not OS-present completion; the main coordinator is separately checking the actual upstream/OS boundary.
