# 审计开发、PR、CI、合并与部署流程

## Goal

基于当前仓库的真实配置、脚本、GitHub 状态和历史运行证据，系统审计从本地开发到发布部署的完整软件交付流程，找出影响开发者体验、反馈速度、合并可靠性和发布效率的瓶颈，并给出符合主流软件工程实践、可按优先级落地的优化路线图。

本任务的价值是让维护者能够区分高收益改进、低价值仪式和仍缺证据的猜测，避免为了“行业最佳实践”引入不适合当前项目规模的复杂度。

## Background

- 仓库是 Rust workspace，同时包含 Vue 3 + Tauri UI、VS Code 扩展和 VitePress 文档。
- 当前分支为 `dev`，任务创建时工作树干净；另有独立的 `07-31-profile-open-command` 任务处于 `in_progress`，本任务不得影响它。
- 根 `justfile` 是本地与聚合质量门入口；GitHub Actions、发布配置和仓库远端状态是本次审计的主要事实来源。
- 用户明确要求检查开发、PR、CI 合并和部署流程在体验与速度方面的优化空间，并与软件工程行业常见做法对照。

## Confirmed Facts

- `main` 和 `dev` 都要求 Root、Vue/Docs、Tauri Linux、VS Code 四个聚合 context；`main` 强制管理员遵守，`dev` 允许管理员绕过。
- Root、Tauri 和 VS Code workflow 仅在 PR 上运行；Frontend 也在 push 上运行。最新 `dev` push 只运行 Frontend CI，而当前 `just version-check` 会因 `ccr-ui/README.md` 版本徽章滞后而失败。
- 2026-07-27 起的 136 个 completed run 样本中，Root/Tauri/Frontend/VS Code 的中位端到端时长分别约为 11.78/14.58/4.73/6.10 分钟。
- PR #42 包含 72 个提交、605 个文件、+53,993/-7,274 行，历时 7.75 小时且无 review；四个 PR workflow 各运行 7 轮。
- 当前 23 个开放 PR 全部为目标 `main` 的 Dependabot PR，其中 12 个 blocked；配置没有 grouping、limit、stagger 或 `target-branch`。
- Release 对任意 `v*` tag 触发，各平台 job 直接写公开 Release；已有 `release` environment 未被 workflow 使用，GitHub deployment history 为空。
- 详细证据、样本定义和限制记录在 `research/repository-workflow-baseline.md`；行业基线记录在 `research/industry-practices.md`。

## Requirements

- R1. 还原本地开发、提交前验证、PR 创建与审查、CI、分支保护与合并、版本发布和部署/分发的实际链路。
- R2. 对每条链路记录入口、触发条件、依赖、质量门、并行/串行关系、缓存、重复工作、人工步骤、失败反馈质量和可观测性。
- R3. 使用当前仓库文件、Git/GitHub 只读状态和可获得的历史运行数据区分“已证实事实”“合理推断”和“缺失证据”。
- R4. 使用官方文档、规范或一方资料建立行业对照基线；不以二手博客作为关键结论的唯一依据。
- R5. 从开发者体验、反馈时延、CI 资源效率、合并安全性、发布可靠性和维护复杂度六个维度评估现状。
- R6. 每项建议必须包含问题证据、建议做法、预期收益、实施成本、风险/取舍、前置条件和验证指标。
- R7. 建议按 `P0/P1/P2` 或等价层级排序，并形成可分阶段执行的路线图；优先低风险、可测量、高收益的改进。
- R8. 输出一份自包含 Markdown 审计报告，包含执行摘要、现状图、发现、行业对照、建议矩阵、实施顺序和验证方案。
- R9. 审计保持只读，不修改产品代码、CI、分支保护、GitHub 设置、发布或部署配置；只允许写入本 Trellis 任务目录内的规划与研究工件。

## Acceptance Criteria

- [x] AC1. 报告覆盖本地开发、PR、CI、合并、发布/部署五个阶段，并指出阶段间的交接关系。
- [x] AC2. 关键现状结论均链接到仓库路径、GitHub 只读查询结果或明确标注的证据缺口。
- [x] AC3. 行业对照结论引用高可信一手来源，并说明其适用条件，而不是机械套用。
- [x] AC4. 至少给出当前瓶颈的优先级排序，并区分体验问题、速度问题、可靠性问题和治理问题。
- [x] AC5. 每项主要建议都有收益、成本、风险和可量化验证指标，维护者可据此决定是否实施。
- [x] AC6. 报告明确列出不建议做、暂缓做或需要更多数据后再决定的事项。
- [x] AC7. 报告经过证据一致性复核，事实、推断和建议没有混写；未获得的运行数据不报告为已验证。
- [x] AC8. 除任务目录工件外，工作树中的其他路径保持不变。

## Out Of Scope

- 实施任何优化建议。
- 创建、更新、合并或关闭 PR。
- 修改分支保护、规则集、GitHub Actions、密钥、环境、Release 或部署目标。
- 运行会产生发布、部署、计费或外部状态变更的命令。
- 对另一个活动 Trellis 任务做归档、提交或状态变更。

## Constraints

- 所有 GitHub 与外部系统操作必须只读。
- 优先读取 `code_map.md` 指向的入口，跳过生成目录和无关大目录。
- 对无法取得的 CI 时长、排队时间、缓存命中率或部署成功率，记录为数据缺口，并给出后续测量方法。
- 结论应与当前项目规模和维护模式相称，避免建议无收益的流程复杂化。
- 当前无阻塞的产品、范围、兼容性或风险决策；进入执行只需用户在最终规划摘要后显式批准。
