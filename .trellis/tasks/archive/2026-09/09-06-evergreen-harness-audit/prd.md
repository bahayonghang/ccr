# CCR 常青维护审查与五套 harness 对齐

## Goal

为 CCR 建立基于当前源码、现有测试和 CI 证据的常青维护计划，并对齐 Claude Code、Codex、Grok Build、Kimi Code、OMP 五套开发 harness。当前仅审查与规划，等待用户批准后实施。

## Requirements

- R1：阅读项目结构、关键代码、验证入口，记录当前提交与工作区基线。
- R2：运行现有测试和只读检查，区分通过、失败、阻塞和未执行；追踪失败工作流根因。
- R3：依据官方来源和仓库配置区分五套 harness 的能力、规则加载、模型选择与证据边界。
- R4：制定按优先级排列的父子任务，每项列出修改文件、依赖顺序、必要检查、强模型审查与低成本执行分工。
- R5：核对 CLAUDE.md、AGENTS.md 和工具专属规则的冲突与缺失；批准项实施后回写项目说明或 skill，并注明适用工具。
- R6：本轮只允许规划产物、测试输出和审查报告；不改产品代码、现有说明或 skill，不安装新依赖、不启动任务、不提交或发布。
- R7：后续仅实施明确批准的子任务，并将验证过的结果、适用工具和未验证边界回写项目说明或现有技能。

## Acceptance Criteria

- [x] AC1（R1）：报告有当前基线、模块图及实际文件依据。
- [x] AC2（R2）：报告有命令、结果、失败原文摘要和根因证据，未验证事项显式标记。
- [x] AC3（R3）：五套工具各有来源、仓库接入情况、可承担工作及限制。
- [x] AC4（R4）：规划时所有子任务保持 planning，具备文件范围、验收命令及执行顺序。
- [x] AC5（R5）：规则缺口有具体改造责任文件和批准后回写机制。
- [x] AC6（R6）：审查轮原有受版本控制文件保持不变；可批准计划已交付。
- [x] AC7（R7）：五个批准子任务已实施、check PASS、独立提交并归档；规则子任务已回写；P2 仅诊断。发布门 `just ci` 见父任务终验。

## Task Map

父任务统一拥有审查证据与集成验收。子任务：evergreen-ui-smoke（R2/R4）、evergreen-ci-verdict（R2/R4）、evergreen-omp-context（R3/R4）、evergreen-harness-rules（R3/R5/R7）、evergreen-ci-history（R2/R4，独立P2）。依赖顺序见 design.md；本轮审查交付不等于后续修复验收。

## Out of Scope

本轮不实施修复、不调用付费外部模型做实测、不操作桌面 UI、不改用户全局规则或团队知识库；后续写回必须依据批准范围。
