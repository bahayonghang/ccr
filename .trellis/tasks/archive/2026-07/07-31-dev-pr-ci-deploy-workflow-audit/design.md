# 审计设计：开发、PR、CI、合并与部署流程

## 1. 交付物与边界

本任务只产出一份自包含报告：

`audit-report.md`

报告位于本任务目录，覆盖本地开发、PR、CI/合并、Release 与实际部署/分发边界。任务不修改产品代码、workflow、GitHub 设置或任何远端状态。

研究输入：

- `research/repository-workflow-baseline.md`：当前仓库与 GitHub 的只读事实快照。
- `research/industry-practices.md`：官方/一手来源构成的行业基线。
- live repository files：用于在执行时刷新容易漂移的路径与配置。

## 2. 证据模型

每条主要结论使用以下标签之一：

| 类型 | 定义 | 允许的写法 |
|---|---|---|
| 已证实事实 | 当前文件、命令输出或 GitHub API 可直接证明 | 给出路径/行号、run/PR URL、时间范围或命令 |
| 合理推断 | 多项事实支持，但没有直接事件或因果证据 | 明确写“推断”，列出依据与替代解释 |
| 证据缺口 | 当前无法取得所需数据 | 说明缺什么、为什么重要、怎样补测 |
| 建议 | 基于事实、约束和行业资料作出的选择 | 不得伪装成当前行为或行业硬标准 |

容易漂移的远端事实（开放 PR 数、分支差异、最新 run、release/environment 状态）在写报告前刷新一次，并注明 `as of` 时间。历史 run 和 merged PR 数据保留捕获时间与样本范围。

## 3. 流程模型

报告用一条端到端链路作为主结构：

```text
本地开发
  -> 提交前验证
  -> PR 创建与评审
  -> required CI
  -> 分支保护与合并
  -> 版本/tag
  -> 原生平台构建与验证
  -> GitHub Release / 其他分发渠道
  -> 发布后验证与度量
```

每个阶段统一记录：入口、触发、依赖、质量门、等待/执行时间、缓存与重复工作、人工步骤、失败反馈、权限/安全、可观测性、与下一阶段的交接合同。

## 4. 评价维度

每个发现从六个维度评价，但只展示有意义的维度：

1. 开发者体验：命令可发现性、反馈可行动性、是否污染工作树、人工切换成本。
2. 反馈时延：first actionable feedback、required gate、queue 与 execution。
3. 资源效率：重复运行、重复安装、缓存收益、取消策略、矩阵并发。
4. 合并安全：required checks、管理员绕过、评审、分支漂移与批量大小。
5. 发布可靠性：版本/tag 校验、artifact 完整性、签名、汇聚发布、恢复能力。
6. 维护复杂度：新增流程的持续成本、当前项目流量是否值得、回退是否清晰。

## 5. 发现与建议合同

主要发现使用稳定 ID：`F-LOCAL-*`、`F-PR-*`、`F-CI-*`、`F-REL-*`、`F-OBS-*`。每项包含：

| 字段 | 内容 |
|---|---|
| 证据 | 仓库路径、GitHub URL、样本范围、事实/推断标记 |
| 影响 | 体验、速度、可靠性、治理中受影响的维度 |
| 根因 | 当前机制为什么产生该结果 |
| 建议 | 最小完整改进，不把可选增强混入首步 |
| 预期收益 | 可验证方向；没有基线时不承诺虚假百分比 |
| 成本 | S/M/L，并解释文件、平台或治理范围 |
| 风险/取舍 | 可能增加的等待、维护、权限或误跳过风险 |
| 前置条件 | 数据、权限、证书、协作者或产品决策 |
| 验证指标 | 改动后比较的 P50/P90、失败率、取消率或发布完整性 |

优先级定义：

- `P0`：当前存在可观察的门禁缺口、发布完整性风险或高浪费，且可用低到中等复杂度修复。
- `P1`：显著改善速度、诊断或治理，但不阻断当前正确性交付。
- `P2`：成熟度增强或依赖未来规模、证书、渠道与历史数据。

## 6. 预期建议边界

报告需要评估但不预设最终结论的方向：

- `dev` push 的完整反馈、管理员 bypass 与 branch strategy。
- stale PR run cancellation、job timeout、工具安装/缓存、前端依赖安装去重。
- Dependabot grouping、limit、schedule 与目标分支。
- PR 模板、评审粒度、release notes 与可量化流程指标。
- Release 的 build/verify/publish 分离、job-level permissions、environment、签名、attestation 与 smoke。

报告必须单列“不建议现在做”：至少评估 merge queue、自托管 runner、更大 runner、强制多人审批、自动 updater 和多渠道部署是否缺少规模或前置条件。行业实践不是默认启用清单。

## 7. 报告结构

1. 执行摘要与最优先的 5-8 项结论。
2. 当前端到端流程图与关键交接合同。
3. 数据样本、指标口径与证据限制。
4. 本地开发与提交前反馈。
5. PR、评审、分支保护与合并。
6. CI 运行时、排队、缓存、重复与失败反馈。
7. Release、分发、部署、供应链与恢复。
8. 行业对照表：当前、常见做法、适用条件、差距。
9. `P0/P1/P2` 建议矩阵。
10. 分阶段落地路线图和每阶段验收指标。
11. 暂缓/不建议事项、证据缺口和后续测量计划。
12. 证据索引与官方来源。

## 8. 校验与回滚

校验重点是证据一致性而非代码门禁：

- 所有主要事实均可追溯到 research、仓库路径或 GitHub URL。
- 所有外部主张有官方/一方来源，并写明适用条件。
- 优先级与证据、收益、成本一致；同一建议不在多处产生矛盾版本。
- 不把 queue time 当成 execution time，不把 SHA256 当成 publisher identity，不把 Release published 当成所有平台部署成功。
- `git status --short` 证明任务目录外没有新增变更。

回滚只需移除本任务目录；报告生成不改变运行时或远端状态。
