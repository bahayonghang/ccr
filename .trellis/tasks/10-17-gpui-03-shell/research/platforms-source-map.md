### Typed dirty-key and CAS contracts

The existing frontend contract is `ccr-ui/src/configs/settings-types.ts:39`: `SettingsSnapshot { values, source, managedLocks? }`; `SettingsSaveInput { values, dirtyKeys, snapshot, environmentId? }`; results saved/conflict/managed_locked/unsupported_environment. The snapshot's `source` stays editor-session-local and may contain secrets. This is a behavior map, not a reason to recreate dynamic TypeScript-shaped dispatch in Rust.

- Claude: `settings-claude.ts:173` maps changed form IDs to payload paths, including `env`, nested permissions/sandbox/attribution. `:181` builds the patch from dirty keys plus original source. Explicit unsupported clearing is rejected, not silently ignored. Backend merge at `commands/claude.rs:126` replaces supplied top-level values; reconstruct changed nested objects against their original source so untouched nested fields survive. Latest-file preservation under replay is provided by SettingsManager for local data; an editor's stale full nested subtree is not automatically a leaf-level CAS contract.
- Codex: `settings-codex.ts:75` sends only dirty payload fields; pure backend application at `commands/codex.rs:1294` updates known supplied fields and handles nested null clearing. Existing field-preservation tests in `codex_settings.rs:51` cover model-only updates and unrelated custom/profile/MCP/TUI/history content. They do not establish CAS or cross-writer safety.
- Grok: `GrokSettingsPatchDto { set: BTreeMap<String, OpenJsonValueDto>, unset: Vec<String> }` (`commands/grok.rs:296`). `settings-grok.ts:129` maps dirty form IDs through `GROK_ID_TO_KEY` and validates only the requested set. Backend validates before I/O, tests whether keys touch MANAGED_SETTINGS_KEYS, reads latest document/token and activation every attempt, refuses managed mutations unless inactive, applies only set/unset paths, secret-writes with no backup and returns Conflict after retry exhaustion (`:1104–1149`). Reuse explicit Saved/Conflict/ManagedLocked/Unsupported outcomes. It currently replays against latest state rather than accepting a draft token for typed edits.
- OpenCode: `settings-opencode.ts:79` separates runtime and TUI patches using original source; two saves are sequential (`:105`), so failure of TUI save after runtime save is possible. Do not claim two-file atomicity. A typed state/result must surface partial outcome or use an existing journal owner if stronger approved semantics require it. Primary/legacy read fallback must be part of the observed revision, not an unconditional copy over a newly appeared primary.
- Raw Claude/Codex: `write_raw_file_versioned(path, backup_dir, prefix, content, expected_token, secret)` delegates to `ccr_core::core::write_guarded_versioned` (`settings_raw.rs:185`). Empty expected token means missing file, not an existing empty file. Written returns new content token; Conflict does not create a backup. Validation returns static error kind/message/position, never raw parser display.
- Raw Grok: identical core CAS primitive with BackupPolicy::None and secret=true (`grok.rs:1180`). Layer metadata and policy entries are informative; typed managed-lock rules must not be mistakenly equated with all raw operations already enforcing policy.

Core primitive owner: `.trellis/spec/ccr-core/backend/atomic-writer.md`, Content-versioned guarded write contract. Keep its same-path leaf lock covering reread/version comparison/backup/replacement and its distinction between Conflict and I/O failure. Do not extend frozen CcrError for an expected conflict or compare outside the lock before unconditional write. External processes that do not join CCR locks remain outside a cross-process transaction guarantee.

### Providers, credentials and diagnostics

- OpenCode providers have **no dedicated baseline Tauri command IDs**. Their TS orchestration is `ccr-ui/src/api/domains/opencode.ts:163` (canonical provider, fallback legacy providers), `:198` list, `:204` add, `:217` merge edit, `:230` delete. Each uses get/update settings. Native must implement the real `/opencode/providers` route and trace it separately; an opencode_update_settings action alone does not prove CRUD parity. Keep unknown provider/options/model fields and enabled/disabled visibility handling (`features/opencode/OpenCodeProvidersView.tsx:139`).
- Non-secret provider templates currently live in TS catalog/types/utils, not the Codex auth store. `utils/providerTemplates.ts:42` and `:84` recursively strip secret-key names from platform overrides; `:95` sanitizes templates before custom localStorage persistence (`:137`, `:158`). Port the actual allowlisted metadata model and matching sanitizer/fixture contracts to a shared Rust owner only where both clients need it. Never put API keys in native UI preferences or template catalog. Builtin catalog is `configs/providerTemplates.ts`; template selector smoke coverage is `ccr-ui/tests/configs/provider-template-selector.smoke.test.tsx`. The old spec's root `tests/provider-templates.smoke.test.ts` command is stale: that file is absent in the inspected tree.
- `crates/ccr-codex/src/models/codex_model_provider.rs:5` derives Debug/Serialize for records containing api_key:String. `CodexModelProviderStoreService::save` locks only after callers load (:53/:94), ignores backup failure, writes without secret(true) then applies permissions; backup uses fs::copy (:76). These are existing credential-store hazards, not newly verified safe patterns. Do not log/derive Debug on native projections of these records or copy their persistence. Any necessary safety correction belongs this existing owner, with Tauri/CLI compatibility regression, rather than a second native credential database.
- Raw config and scoped secret editor deliberately contain plaintext. Keep their entity lifetime scoped and clear on account/environment change; exclude from Debug, generic error formatting, command history/recent UI state and persisted drafts. Existing `.trellis/spec/ccr-codex/backend/codex-provider-bearer-runtime.md` explicitly distinguishes allowed raw/editor plaintext from forbidden status/dashboard/log/template leakage.
- Default TOML/parser formatting can include source secret text: examples are Codex read `commands/codex.rs:832`, provider store `codex_model_provider_store.rs:45`, import `codex_auth.rs:749`. Native error projection must remain static/safe; use field/position or typed classifications, not raw formatted error strings. Existing raw-save code is the positive pattern.
