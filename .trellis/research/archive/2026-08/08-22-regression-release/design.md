# 技术设计：全量回归与 Tauri 打包验证

> 父任务：`08-22-react-migration`（阶段 7，最后一个子任务）。本文件写逐屏比对方法、平台覆盖范围与验证顺序。

## 1. 逐屏比对方法

185 个界面，约 20 工程日，是本任务的主体工作量（PRD Notes）。

### 1.1 基线来源

比对基线为 `dev` 分支迁移前的构建产物。基线在父任务的基线采集门产出（父任务 `implement.md` §4 阶段 0），落在 `.trellis/tasks/08-22-react-migration/baseline/`：

- 185 个界面在明暗两套主题下的截图。
- 关键交互录屏：5 条缓存路由的离开与返回、OAuth 向导完整流程、日志流实时输出、图表时间范围切换、大表单输入。
- 启动耗时、首屏渲染耗时、bundle 体积三项数值。

基线未采集则本任务的 AC1 与 AC14 无对比依据（父任务已把该项列为阶段 0 → 1 门的准出条件）。

### 1.2 对照依据不是目录浏览

目录结构为全量按域聚合重组（父任务 `design.md` §2、§12.1），185 个文件同时更换框架与位置。因此逐屏比对按 `08-22-react-foundation` 的 `path-mapping.md`（216 行映射表）对照，不按目录浏览——按目录浏览会漏掉移交统一层的 20 个文件所对应的界面。

### 1.3 七个比对批次

按七个视图子任务的域划分（PRD Notes），每批次产出独立记录：

| 批次 | 域                                 | 对应子任务                  |
| ---- | ---------------------------------- | --------------------------- |
| 1    | Claude Code                        | `views-claude`              |
| 2    | Codex                              | `views-codex`               |
| 3    | Grok / Gemini / OpenCode / generic | `views-secondary-platforms` |
| 4    | CheckIn                            | `views-checkin`             |

统一层的 7 个功能面（`platform-unify`）的界面分散在批次 1–3、6–7，按平台归入对应批次。统一层的「平台 × 功能面」验证矩阵（`platform-unify` AC6）已覆盖功能正确性，本任务的批次只做视觉与交互比对，不重复功能验证。

### 1.4 五个比对维度与判定

维度（PRD Scope 表）：行为、视觉、交互、动效、响应式。

每处差异判定为三类之一：

| 判定     | 处理                                                                              |
| -------- | --------------------------------------------------------------------------------- |
| 一致     | 记录并通过                                                                        |
| 有意改进 | 记录改进内容与依据（如 shadcn/ui 原语带来的焦点环变化）。需说明为何是改进而非回归 |
| 回归缺陷 | 登记到缺陷清单，修复后重验（AC2）                                                 |

未判定项为 0（AC1）。「未判定」指该界面或该维度未被检查，不指判定困难——判定困难的项归「有意改进」或「回归缺陷」，需给出结论。

## 2. 平台覆盖范围

Windows 为主验证平台（当前开发环境为 Windows 11 Pro 10.0.26200）。

macOS 与 Linux 的验证范围（PRD 要求在本文件确定）：

| 平台    | 范围                                                                   | 依据                                                                                                                               |
| ------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Windows | 全部 185 界面 + 全部四项运行时验证 + WSL 管理                          | 主开发与主验证平台                                                                                                                 |
| macOS   | 打包成功 + 应用可启动 + 窗口 chrome 六项 + 5 条缓存路由 + 明暗主题切换 | 窗口 chrome 与原生外观是平台差异最大的面（`nativeWindowAppearance.ts` 有平台分支）。界面逐屏比对不重复做——React 渲染结果与平台无关 |
| Linux   | 打包成功 + 应用可启动 + 窗口 chrome 六项                               | WebView 实现与 Windows / macOS 不同（WebKitGTK），启动与窗口是主要风险面                                                           |

WSL 管理功能仅在 Windows 验证（PRD Scope）。

macOS 与 Linux 的验证若无可用环境，该项标为「未执行」并说明，不标为「通过」。跨平台安装包的分发与签名不在范围（Out of Scope）。

## 3. `just ci` 的构成

本任务 `prd.md` 的 Scope 与父任务 `implement.md` §2.1 一致：迁移前基线为 13 步。

```
version-sync → version-check → fmt → fmt-check → lint-strict → check-workspace
→ test → release → audit → ci-governance-check → tauri-bindings-check
→ frontend-check → vscode-ci
```

`08-22-arch-quality-perf` 批次 5 把 `frontend-coverage` 纳入 `just ci`（插在 `frontend-check` 之后），因此本任务执行时应为 **14 步**。

**判定权威是 `just ci` 的实际 recipe 依赖清单与退出码**，不是步数（父任务 `implement.md` §2.1 的口径）。AC8 核对「实际清单与 `justfile` 一致 + 退出码 0」，步数仅作对照并记录。

## 5. 长时间运行验证（R10）

连续运行 2 小时，切换 20 个以上界面。采集两项：

- 内存占用无持续增长。采样间隔与判定阈值需定——「无持续增长」的可操作判定为：后半段（第 2 小时）的内存均值不高于前半段均值的 110%。
- 事件监听器数量稳定。计数方式复用 `08-22-state-logic-port` §7 的 mock 计数手段，或在打包产物中用 Tauri 侧的监听器统计（若有）。后者需确认可行性。

该验证覆盖 `08-22-views-sync-tools` AC7（30 分钟日志流内存）之外的全局泄漏——两者的检查面不同，都需执行。

## 6. 性能对比（R11）

迁移前后的启动耗时与首屏渲染耗时对比落盘（AC14）。数据来源：

- 迁移前：父任务基线采集门的三项数值。
- 迁移后：`perfTelemetry.ts` 的采集能力保留（R11），在打包产物上采集。

`08-22-arch-quality-perf` 批次 7 的五个性能场景中，场景 1、3、4 依赖的视图在该子任务执行时尚未迁移，其 React 侧数值由本任务补测（该子任务批次 7 已注明）。因此本任务需跑全部五个场景的 React 侧测量，与 Vue 侧基线对比。

性能回归若超出可接受范围，登记为独立任务（Out of Scope：本任务只测量与记录，不做优化）。「可接受范围」的取值来自 `perf-baseline.md`；该文件未给阈值时，本任务记录差值并交由父任务判定。

## 9. 验证顺序

顺序有依赖，不可任意调整：

```
1. just ci 全绿（14 步）          ← 代码级门，先过
2. just tauri-build 产出安装包     ← 后续验证都需要产物
3. 安装并启动
4. 四项运行时验证                  ← 需要产物
5. 七批次逐屏比对                  ← 主体工作量，在产物上做
6. 回归缺陷修复 → 回到步骤 1        ← 修复后需重跑 ci
7. 2 小时长时间运行                ← 在无回归缺陷的产物上做
8. 性能与预算测量
```

步骤 6 的回环是本任务耗时的主要不确定性来源：每轮回归缺陷修复后需重跑 `just ci` 与重新打包。因此缺陷修复应批量进行，不逐个修复逐次重跑。
