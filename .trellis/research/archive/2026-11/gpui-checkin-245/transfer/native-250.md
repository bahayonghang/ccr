# Windows 原生签到配置传输验收

默认功能 release 构建来自 `b1d89e54c9edb6a144e64b1c7eb1502cc8905331`，可执行文件 SHA-256 为 `df667518495a1becdd58e8da499d0349a205eddbc7c8f0129ff326d2ca53e208`。在两个独立的 Windows 私有桌面打开中文浅色窗口，客户区均为 1280 × 800 逻辑像素。两次都通过普通成对夹具启动，从侧栏进入「签到管理」，在真实路径输入框输入临时目录内的绝对路径。[工单 #250](https://github.com/bahayonghang/ccr/issues/250)

| 操作 | 窗口与文件的实际结果 |
| --- | --- |
| 缺库预览、取消 | 预览显示将在本机创建数据库，新增 1 个提供商和 1 个账户，冲突均为 0，并提示源文件含明文 Cookies。预览后及取消后分别检查，数据库、WAL、SHM、密钥目录、迁移目录和锁目录均不存在。 |
| 确认导入 | 再次预览并提交后，回执显示导入 1 个提供商和 1 个账户。回到账户分段可读到合成账户 `Transfer Demo`。 |
| 默认跳过、显式覆盖 | 把源账户名称改为 `Updated Transfer Demo` 后重新预览，提供商和账户各有 1 项冲突。按默认策略提交后各跳过 1 项，本机账户仍为原名。单独选择覆盖并确认后各导入 1 项，主库中的账户已改名。 |
| 离线恢复验证 | 根据覆盖回执给出的具体文件名，将验证备份复制到另一隔离目录，以只读方式打开。恢复副本中的账户保留覆盖前的名称，用原设备夹具密钥能解密并比对合成 Cookie。操作后主库中的账户仍为新名称。 |
| 两种导出与撞名 | 新配置文件中有 1 个账户，Cookies 标记为已加密，文件中无明文哨兵。向同一文件导出统计得到了目标已存在提示，原文件逐字节一致。改用新路径后，今日统计 JSON 读到 `total_accounts = 1`。 |
| 已有库的首次导出 | 在第二个隔离目录使用已有库、无迁移目录。首次操作直接导出今日统计成功，未创建迁移目录。原生运行时回归还逐字节比对了两种导出前后的源数据库。 |

主场景读取了 42 次 Windows UI Automation 控件树，已有库场景读取了 7 次。检查可访问名称、帮助、状态、可读值与文档文本，两个窗口的输出日志各为 0 字节。三张截图均已打开核对，路径、提示和回执未显示合成凭据。此次窗口证据覆盖中文浅色 Windows；没有操作真实提供商、个人凭据和生产数据库。

## 回归复现与检查

- 原生控件回归最初在缺库预览后发现真实创建了 `checkin.db`。修复后还通过切换分段、重新输入路径并预览缺失文件，验证迟到结果不能恢复旧预览。
- 共享导入器曾在首次建池失败后留下没有签到表的库，使重试报 `no such table`。同目录准备初始 schema 后原子拒覆发布，可以重新预览并重试。其他客户端先建库、源字节变更或目标根变化均要求重新预览。
- 同名异 ID 曾使导入账户仍指向外部提供商 ID。回归同时验证默认跳过和显式覆盖后的本机关联。数据库触发器另在第二行制造失败，回执记录实际已保存的第一行，验证备份保留失败前内容。
- 已验证源文件后、宿主打开数据库期间移除已有密钥，曾触发创建替代密钥。回归确认当前提交会失败，原有密文保持，未创建替代密钥或备份。
- 已有库首次导出统计曾通过真实窗口复现迁移目录凭空出现。改用只读数据库连接后，使用相同窗口操作重验通过。
- `cargo test -p ccr-checkin -p ccr-core -- --skip export_bindings` 通过。签到 97 项，共享核心含集成和文档测试 160 项，沿用 8 项 ignore。
- `python ccr-desktop/scripts/desktop.py cargo test --locked --lib checkin:: -- --skip export_bindings` 通过 23 项。`just desktop-test-ui` 和 `just desktop-ci` 通过，后者的 GPUI 库测试通过 469 项，沿用 4 项 ignore，并产生本次验收的 release 程序。
